VR Adult Fix fare source — Phase 1 technical report

Live investigation date: 2026-08-25 (Europe/Stockholm). Scope: read-only official VR searches between Göteborg C and Stockholm C.

1. Verdict

Direct API/client feasible. A fresh headless browser was useful only to derive and verify the request. Routine fare acquisition does not require browser automation, login, cookies, tokens, CAPTCHA handling, or a visible/local browser.

2. Evidence

The official booking frontend uses:

POST https://api.vrresa.se/api/v1.0/departures/

Observed Adult one-way request body:

{
  "origin_id": "<VR station UUID>",
  "destination_id": "<VR station UUID>",
  "date": "YYYY-MM-DD",
  "for_outbound": true,
  "passengers": [1],
  "has_stroller": false,
  "has_pet": false,
  "wheelchairs": 0,
  "walkers": 0
}

The UI's “1 Adult” state generated passengers: [1]. The useful response fields are:

  • [].departures[].schedule_reference: service/train number.
  • [].departure_at and [].arrival_at: timezone-aware ISO timestamps; duration can be derived.
  • [].prices.FIX: Adult Fix amount for this request. The official Swedish UI renders it as kr, and its analytics identifies the currency as SEK.
  • available, bookable, seats_left: sale state.
  • has_disruption, had_rebooked_disruption, plus per-service event, messages, transport_type, traffic_provider, and nested legs[].vehicle_types: operational/anomaly information exposed by the API.

HAR requests contained no Authorization, CSRF token, API key, or Cookie on the departures call. A direct replay succeeded after explicitly removing Referer, Accept, User-Agent, and all session state; only JSON Content-Type was retained.

3. Reliability

The direct client succeeded for six live searches: both directions on 2026-08-26, 2026-08-27, and 2026-08-31. Four official UI searches were checked: Stockholm→Göteborg on 08-26 and 08-31, and Göteborg→Stockholm on 08-27 and 08-31.

4. Minimal proposed fare architecture

  1. Resolve a small controlled station alias to the station UUID observed in VR's official booking URL.
  2. Send one low-rate JSON POST per route/date to /api/v1.0/departures/.
  3. Return every discovered journey; do not filter by assumed timetable.
  4. Normalize train numbers, timestamps, calculated duration, availability, prices.FIX as Adult/SEK, and all exposed anomaly fields.
vr-fares search --from GOTEBORG --to STOCKHOLM --date YYYY-MM-DD

5. Risks

  • The endpoint is an internal, unversioned frontend API despite the v1.0 path; schema, station IDs, and passenger codes may change without notice.
  • No auth/session expiry risk was observed, but VR could add access controls later.
  • No CAPTCHA, throttling, or headless-only blocking was observed at this low rate. Higher-frequency behavior was intentionally not tested.
  • Tests were run from Sweden; geography-dependent CDN, pricing, or controls were not tested.
  • All sampled journeys had has_disruption=false. The API exposes relevant fields, but the exact encoding of a real reroute or replacement bus remains unvalidated.
  • prices.FIX may be absent even when a journey remains bookable=true; consumers must preserve null/unavailable rather than treating it as zero.
  • Currency is rendered by the official UI as SEK/kr rather than repeated on each API price object.

6. Recommendation for Phase 2

Proceed with the direct client as the primary acquisition method. Add conservative scheduling/backoff, schema-contract checks, explicit null handling, and occasional browser-based canary comparisons. Add a captured real disruption/replacement-transport fixture when one naturally appears. Retain headless browser derivation as a maintenance fallback only; existing/local Chrome control is not currently justified.
